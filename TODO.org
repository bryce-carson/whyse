** SQL Commands
WHYSE needs a flexible, intuitive way to accept SQL commands from the user and
send them to SQLite.

Using three approaches allows user flexibility: associate a comint REPL with the
SQLite database (=sql-comint-sqlite=); accept queries from the minibuffer;
execute queries using a command API.

The command API would facilitate the second approach: any query string given by
the user in the minibuffer would be evaluated. Likewise, predefined queries
would be evaluated using the same function.

*** Carbon copies of the tool syntax
When conducting business on paper using a (carbon) copy pad is commonplace to
produce a copy of a document---such as a form or a receipt---for both customer
and business records. =carboncopy= is such a filter, which copies the tool
syntax it receives to a file named in the shell variable =CARBONCOPY= and then
passes its input to its output.

It is a wrapper around the command =tee=, ensuring =CARBONCOPY= is set and
non-null and that noclobber is not set.

#+begin_src bash :tangle carboncopy :shebang #!/usr/bin/env bash
  if [[ -n ${CARBONCOPY:?"shell variable is unset or null!"} && !$(echo $SHELLOPTS | grep noclobber) ]]; then {
      tee </dev/stdin $CARBONCOPY
  }
  fi;
#+end_src
** The stages in the /notangle/ pipeline
The wrapper script =notangle= has hardcoded paths to =markup= in the =LIBEXEC=
of Noweb, set at build time. The wrapper parses the arguments and constructs the
pipeline.

1. Convert the web to a machine-readable (tool) format using =markup=.
2. Extract the desired code chunk with =/usr/libexec/noweb/nt=.

=nt= is the binary backend serving the =notangle= shell script. =nt= therefore
depends upon =markup=. =markup= is also a binary.

#+name: notangle
#+begin_src shell
  #!/usr/bin/sh
  # Copyright 1991 by Norman Ramsey.  All rights reserved.
  # See file COPYRIGHT for more information.
  LIB=/usr/libexec/noweb
  markup=$LIB/markup opt= arg= markopt= filters=
  while [ $# -gt 0 ]; do
          case $1 in
          -gitversion) echo "50840b12b87af91fe9aea6b4979ea7f71286b5be" ; exit ;;
          -ml|-m3|-awk|-icn|-icon|-pascal|-c|-c++|-f77|-f90|-tex|-w[0-9][0-9]*) ;; 
                                          # deliberately ignore nountangle args
          -t)  ;; # this is default
          -t*) markopt="$markopt -t" ; opt="$opt '$1'" ;;
                  # copy tabs at markup, use width given in notangle
          -filter) filters="$filters $2 | " ; shift ;;
          -markup) markup="$2" ; shift ;;
          -)   arg="$arg '$1'" ;;
          -L*) opt="$opt -t '$1'" ; markopt="$markopt -t" ;;
          -*)  opt="$opt '$1'" ;;
          ,*)   arg="$arg '$1'" ;;
          esac
          shift
  done
  PATH="$PATH:$LIB" 
  export PATH
  eval "$markup $markopt $arg | $filters $LIB/nt $opt "'; rc=$?'
  exit $rc
#+end_src

** The stages in the /noweave/ pipeline
This is an example of a particular noweave pipeline which includes
indexing of code in the C language for identifiers and
cross-references between chunks.

1. Convert the web to a machine-readable (tool) format.
2. Identify definitions of identifiers.
3. Find usages of identifiers.
4. Create an index of identifiers and cross-references.
5. Generate LaTeX.

** The stages in the /whyse/ pipeline
This is hypothetical.

#+begin_src sh :var WEB="~/src/whyse/src/whyse.nw"
  markup WEB | autdefs elisp | finduses -noquote | noidx
#+end_src

1. Convert the web to a machine-readable (tool) format: ~markup WEB~.
2. Identify definitions of identifiers: ~autodefs elisp~.
3. Find usages of identifiers, skipping uses in quoted code (documentation): ~finduses -noquote~.
4. Create an index of identifiers and cross-references: ~noidx~.
5. Generate Emacs LISP.
   1. Convert code and documentation chunks into widgets.
      1. Documentation chunks are largely preserved as plain text; quotations and cross-references may need special handling.
      2. Code chunks are converted to widgets using plain text.
6. Evaluate the Emacs LISP.
7. Modify the web source buffer using whyse-mode.
8. Export the buffer to a web.
   1. Convert widgets to plain text.
      1. Chunk definition widgets contain "<<chunk-name>>=", which can be written directly; the rest of the widget data isn't exported.
      2. Documentation chunks are already plain text.
   2. Save the buffer to a file.
9. Repeat steps 1--8 until the program and its documentation is complete.

** Module trees
What is WHYSE? What am I doing? I am working on a lisp program that will allow
navigation between modules, which are represented as vertices in a directed
graph. These vertices and their adjacent edges can be represented in a number of
ways, but I should follow something proven. I will need to establish the
polyforest. A polyforest is just a list of forests. A forest is just a tree with
multiple roots. On representations of graphs in computer science:
https://en.wikipedia.org/wiki/Adjacency_list;

#+begin_src elisp
  (defun w--module-navigate (widget direction widget-number)
    "Navigate to another module.

  Navigate to a module, previous or next, from the current module's action
  button."
    (let ((widget-number (widget-get widget :module-number)))
      (if (and (stringp direction)
               (string= direction "prev"))
          (while; not at the beginning or end of the buffer, nor at the desired widget
              (or (not (bobp))
                  (not (and (widget-at)
                            (widget-member (widget-at) :module-number)
                            (= (widget-member (widget-at) :module-number)
                               (1- widget-number)))))
            (backward-line))
        (while; not at the beginning or end of the buffer, nor at the desired widget
            (or (not (eobp))
                (not (and (widget-at)
                          (widget-member (widget-at) :module-number)
                          (= (widget-member (widget-at) :module-number)
                             (1+ widget-number)))))
          (forward-line)))))

  (widget-create 'push-button
                 :format "%[prev%]"
                 :button-face custom-button
                 :module-navigate #'w--module-navigate
                 :action (lambda (widget value)
                           (widget-apply widget :module-navigate
                                         value
                                         (widget-get widget :module-number))))
